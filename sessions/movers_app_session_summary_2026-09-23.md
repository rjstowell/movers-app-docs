First cut moved escalated runs to `auto_send_failed`, which took them out of the Escalated tab with nowhere to go; fixed before merge.

Throws `AutoSendFailure` with `recipient_suppressed_bounce` / `_complaint`; the cron passes it through instead of wrapping as `provider_error`. New `retryable` flag beside `SEND_FAILURE_REASONS` hides Retry. New `dismissFailedQueueItem` for non-retryable failed rows (writes `discarded`, sets `error_resolved_at` so the health count clears).
- **Verified on prod:** Postmark test payloads -> rows + alarm email; replayed event -> no duplicate, reason kept; POST without creds -> 401 (GET gives 405, route only accepts POST); real send via the Postmark API to `hardbounce@bounce-testing.postmarkapp.com` from S199's verified sender -> real bounce ID row in 15s; manual suppression of the test address -> approve blocked before the transport with the readable reason.

## 3. S352: bounce suppressions are strikes, not bans (PR #138, `a00a647`)

- **Migration** `20261226090000_s352_bounce_strikes.sql` (applied stamp `20260923`): `active`, `strikes` (>= 1), `cleared_at`, `cleared_by` on `email_suppressions`. Existing rows backfilled active / 1 strike.
- **Design:** a hard bounce is evidence, not a verdict. Only active rows block. Owner/admin can clear a bounce row ("Address is correct, send anyway") which calls Postmark's reactivation endpoint (`POST /message-streams/outbound/suppressions/delete`; a 200 can still carry a per-address failure, the client treats anything but `Deleted` as failure; an address Postmark never had comes back `Deleted`) and only then sets `active=false`. Fail closed if Postmark refuses. Each new bounce re-activates and adds a strike; at 3 the tenant cannot clear (support only). Spam complaints can never be cleared by a tenant (Postmark refuses by API too). Replayed bounce IDs do not add strikes; strike/clear updates are conditional on the strike count not having changed.
- **Codex improvements accepted:** the clear action takes a run id, not an email (an email parameter would let any owner clear any address on the shared list); locked bounces get their own codes (`recipient_suppressed_bounce_locked`, `recipient_bounced_locked`) so the card renders correctly after reload with no details object; a blocked escalated reply now stays in Escalated instead of recording `manual_send_failed`.
- **Copy:** "This address bounced as undeliverable on {date}. If you have checked it is correct, send anyway." / 3 strikes: "This address has bounced 3 times and is blocked. Contact support if you believe it is correct."
- **Verified on prod:** blocked approve shows the dated line + button; click -> row `active=false`, `cleared_at`, `cleared_by` = operator user id, reply sent through Postmark (`sent` with MessageID). Locked and complaint branches unit-tested only (no way to send to a chosen address from the app; see S354). Test rows deleted.
- Known edge, accepted: a queue row records its code at failure time; if the address reaches 3 strikes elsewhere afterwards, the button can still show and the server returns the locked error.

## 6. F52 resized (read-only check, no code)

Question from the operator: why reconcile automatically when tenants can delete templates and categories, and untick Active, in the Agents UI? Codex's read-only check: deactivating is durable and fully excluded from classification and drafting (`loadClassifierPromptInput.ts:65` loads `active=true` only; `classify.ts:46-48` rejects inactive keys; `computeDraft.ts:349-351` cannot reach a template under an inactive category). Deleting a category is blocked while templates use it (`deleteCategory`, `actions.ts:1511`); templates FK is `on delete set null`; essential fields link by key with no FK. **Deleted library rows come back** for tenants whose onboarding status is `skipped`: the provisioning RPC is insert-if-missing and both `completeAgentOnboarding` and `provisionPartialOnboarding` can run again for them (the F9 checklist row is the way in). Completed tenants cannot reach it from the UI. Automatic reconcile only mattered if the services checklist were editable post-onboarding, which it is not (S163 cluster). **F52 CLOSED as a feature; replaced by S356 (tombstone deleted library keys so the RPC skips them), post-launch.** Interim guidance: deactivate rather than delete. The "route policy overwrites `quote_request` templates" side effect Codex flagged is the dead block F51 already found (keys renamed to `removals`, matches nothing).

## 7. Process notes
