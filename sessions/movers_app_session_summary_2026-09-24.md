## 2. S358 DONE: extraction timeout and silent fallback (PR #141 `795cdb4`)

23 of 97 enquiries had every `extracted_info` field `missing` although the body carried postcodes, addresses, dates and lists. Fingerprint: exactly the base field shape with no `pickup_routing_hint` key. Cause (Codex, timing probe): `ESSENTIAL_INFO_EXTRACTION_TIMEOUT_MS = 12000` on a gpt-5-mini call that takes 8 to 15s, with the SDK's hidden `maxRetries: 2`, then `computeDraft` caught the throw and drafted from `fallbackMissingExtraction`. A second, rarer failure: reasoning consumed the whole 2000-token budget and returned empty content. **A logger bug hid all of it:** `JSON.stringify(err.error).slice` crashed on a real SDK timeout (`err.error` undefined), so Vercel logged "Cannot read properties of undefined (reading 'slice')" instead of "timed out" for a month.

Fix: 2 attempts x 20s inside a hard 40s ceiling (cancels the in-flight call), SDK retries off, `max_completion_tokens` 4000, logger fixed with regression test, **no fallback**: extraction failure now records the run as errored (`transient`, existing auto-retry schedule 10/30/60 min to 24h then stranded + alarm), no draft, escalations still pass through. Test panel shows "We couldn't read the move details from this enquiry in time". `reasoning_effort` untouched (parked as the lever if timeouts recur). Verified live: three INBOX.Shadow emails (rich, form-style, thin) all extracted correctly; the 23 historical blank drafts were left alone on purpose.

Follow-up raised: **S359 OPEN**: `classifyEmail` and `extractGreeting` still use unbounded `callLLM` (SDK default 10 min), and mailbox sync / auto-replay process several runs inside one 60s function. A run measured 49s end to end today. Before stranger-tenant auto-send.

## 3. S360 DONE: three-state essential info + postcode-only pickup (PR #142 `fb27009` + migration)

Decision B, locked with the operator: (B1) postcode present = pickup `present`, street/area only = `partial`, ask for the postcode only, never "the full address"; (B2) item list completeness comes from signals, not length: the Make classifier's rule 2 ported verbatim (10+ pieces with no hedge, scope-closing words "only / just / nothing else / that's everything", or room-by-room; short list without a closing word = partial; hedges like "etc" / "plus more" = partial); (B3) list, photos and survey are alternatives, so a full list drops the photos ask AND the survey-dates ask.

Build: `list_completeness` promoted from reasoning text to a structured classifier field (spine v5, snapshots updated) and consumed by extraction; status is `present | partial | missing`; draft asks "The postcode for <what they gave>" for partial pickup and "Can you confirm that's everything on the list, or send a few photos if that's easier?" for partial list (replaces both list and photos asks). Two clarifying lines added to the ported rule after repeat-run instability ("count pieces, not kinds"; "an uncounted 'rest boxes' tail isn't a scope-closer"), then 3/3 stable. `pickup_address` field `prompt_hint` set on all six tenants via migration `20261227090000_s360_pickup_postcode_hint.sql` ("The postcode is enough for now if the full address isn't confirmed."). Sapphire (95dac598, "this lists about 85% of belongings") stays partial by design. Divergence noted: Make escalates a full list to a human; the app drafts an acknowledgement and a human still quotes.

## 4. S361 DONE: routing hint keeps the town; no postcode ask when distance resolved (`fe304f0`, `5170019`)

Live test of S360 exposed it: "3 Greenbank Crescent, Newquay" became hint "3 Greenbank Crescent", Google matched a Greenbank Crescent 546 miles away, `resolved_approx`, and the draft's postcode ask was the only thing between that and a wrong-distance quote. Fix: hint and partial value always carry the town ("<street>, <town>"); partial pickup + `resolved` / `resolved_approx` = no ask; ask stays for `no_postcode` / `lookup_failed` / no distance rule. Second commit: a pickup marked `present` is downgraded to `partial` unless its value has postcode-shaped text (guards an inconsistent model; known edge: UK road numbers like "A30" match the outward-code shape, acceptable). Verified live: 29.4 mi Helston depot to Newquay, access ask only.

## 6. F59 DONE: the voice pass (PR #143 `586f952` + migration), DEC59 candidate

Operator question: is the patched-together copy too rigid for tenants who want a different voice? Prior record checked (Candidate C, 4 to 9 Aug): freehand rejected for inventing content; the Make scenario is templates + routing, not freehand; D5 two-register seed rejected as a doubling tax. New answer: **deterministic content, LLM voice.** Skeleton (classify -> template -> dynamic block) is the record of what the reply says; an optional per-tenant pass rewrites wording only, validated against the skeleton (every ask present by structured keywords, no digits/currency/price/miles/survey introduced, signature byte-identical, greeting kept, body length 0.6 to 1.5x, no lists unless the skeleton had one, no dashes, no control characters), skeleton stands on any failure.

Build (Claude Code): `tenant_feature_flags` table (service-role write only, tenant-readable; `tenant_config` UPDATE is owner-writable so the flag could not live there), `tenant_config.voice_instructions`, queue columns `skeleton_body_html` (trigger-immutable), `voiced_body_html`, `voice_status` (none | claimed | applied | failed | reverted), `voice_failure_reason`, `voice_applied_at`, `voice_attempts`, `voice_context` (asks saved at draft time). Async sweep cron, one row at a time, atomic claim, conditional-write RPC that refuses if the row resolved or is within 60s of `send_after` (guards the auto-send race), stale claim after 5 min. ## 7. Lessons

- Measure the thing the operator saw, not the thing the query found first. "22% blank-outs" was true and still undersold the problem by a factor of three until form fields were counted.
- A logger that crashes on the error path hides the error class entirely. The month of "reading 'slice'" logs looked like a code bug, not a timeout.
- Prompt rules that flip on repeat runs are not rules. Run 3x before calling a prompt change done (S360 needed two clarifying lines; S365 needed the same discipline).
- A tenant-visible feature that can fail must say why in the tenant's words, or the tenant concludes it is broken (S365 A).
- Codex/Claude Code replays are slow because they are real LLM calls: 30 minutes for a "small" prompt change is mostly waiting, and the stability re-runs are the part worth paying for.
- Five hand-applied migrations in a day is fine; forgetting to count them for S130 is not. All five are listed in the backlog amendments.
